# HUD layout tokens: studio → JSON → CSS

The combat HUD's tunable look is a fixed set of CSS custom properties, one JSON
file per form factor. The HUD Component Studio (`tools/hud-component-studio/`)
exports those files; `tools/hud-layout-css.mjs` turns them into
`styles/hud-layout.generated.css`, which the game loads after its other
stylesheets. Nothing else writes these properties.

```
studio (Export CSS JSON) ──► ~/Downloads/<form-factor>.json
                                   │  node tools/hud-layout-css.mjs --merge <files>
                                   ▼
                            content/hud-layout/<form-factor>.json
                                   │  node tools/hud-layout-css.mjs --write
                                   ▼
                            styles/hud-layout.generated.css ──► game
```

## Form factors

`<html data-form-factor>` is written by `applyUiScale` in `src/main.js`, the
single layout decider (no new media queries). Thresholds live in
`balance.ui.uiScale.formFactor`, measured in CSS px of the window:

| Form factor | Rule (first match wins) | Reference viewport |
|---|---|---|
| `widescreen` | aspect (w / h) ≥ 2.0 with w ≥ 1600 (landscape phones are not widescreen), or w ≥ 2400 | 2560 × 1080 |
| `mobile` | w ≤ 600 | 390 × 844 |
| `tablet` | w ≤ 1100 | 820 × 1180 |
| `desktop` | otherwise | 1440 × 900 |

## File format

`content/hud-layout/<form-factor>.json`, one per form factor, all four always present:

```json
{
  "format": "ashenspire-hud-layout/1",
  "formFactor": "mobile",
  "source": "hud-component-studio",
  "tokens": { "--hud-text-shadow": "0 1px 2px #000", "--hud-player-details-dx": "0px" }
}
```

A file sets only the tokens it overrides. A studio export passed to `--merge`
may also give a token the value `null`, meaning *remove this override*: the
merge deletes it from the content file and the token returns to its default.
A committed content file never holds `null` (`--check` and `--write` refuse it).
Unknown token names, a wrong
`formFactor`, or a value that fails its type check are errors (the generator
exits 1 and names the file and token). Values are plain CSS text, never `;`,
`{`, `}`, `<`, `url(` or `expression(`.

## Generated CSS

```css
/* GENERATED by tools/hud-layout-css.mjs from content/hud-layout/*.json — do not edit */
:root { --hud-text-shadow: …; /* every token at its default */ }
:root[data-form-factor='mobile'] { /* mobile.json overrides */ }
:root[data-form-factor='tablet'] { … }
:root[data-form-factor='desktop'] { … }
:root[data-form-factor='widescreen'] { … }
```

Defaults reproduce the look before this pipeline existed, so an empty file
changes nothing. `--check` fails when the file on disk differs from the
generated output; `tests/run-node.mjs` runs it.

## Tokens

Types: `shadow` (CSS shadow list or `none`), `color`, `length` (`px`/`%`/`rem`/`em`
number, or `none` where noted), `px` (signed number + `px`), `font` (font-family
list), `keyword` (listed values).

| Token | Type | Consumer |
|---|---|---|
| `--hud-text-shadow` | shadow | HUD text: header HP value, turn ribbon label, idle enemy intent/HP values, enemy names, player HP values, details panel text, Combat log / Reaction labels, footer labels |
| `--hud-text-plate-bg` | color | Backing plate behind the idle enemy HP value and the player's near-feet HP value (`transparent` = off) |
| `--hud-text-plate-radius` | length | Radius of that plate |
| `--hud-text-plate-pad` | length | Horizontal padding of that plate |
| `--hud-panel-bg` | color | Selected player details panel, selected enemy nameplate, intent bubble |
| `--hud-panel-shadow` | shadow | Same panels, plus the Combat log / Reaction row backing |
| `--hud-panel-radius` | length | Same panels |
| `--hud-player-panel-border` | color | Selected player details panel border |
| `--hud-enemy-panel-border` | color | Selected enemy nameplate / intent bubble border |
| `--hud-details-font` | font | Selected player details panel text |
| `--hud-details-name-size` | length | Its name line |
| `--hud-details-value-size` | length | Its HP / Poise / Ward values |
| `--hud-details-label-color` | color | Its POISE / WARD labels |
| `--hud-details-min-width` | length | Its minimum width |
| `--hud-tools-bg` | color | Backing behind the Combat log / Reaction row (`transparent` = off) |
| `--hud-header-hp-max-width` | length or `none` | Header HP bar maximum width |
| `--hud-tools-span` | keyword `field` \| `hand` | Combat log / Reaction row spans the whole field width or only the card band |
| `--hud-player-details-dx` | px | Offset added to the player details panel after placement |
| `--hud-player-details-dy` | px | 〃 vertical |
| `--hud-enemy-nameplate-dy` | px | Offset added to the selected enemy nameplate |
| `--hud-turn-ribbon-dy` | px | Offset added to the turn ribbon |
| `--hud-tools-dy` | px | Offset added to the Combat log / Reaction row |

The `px` geometry tokens are read once per layout pass with
`getComputedStyle(combat).getPropertyValue(...)` by the JS that already places
those elements, added after placement, and then clamped by the same
reachability/clearance rules (an offset can never push a control off-screen or
under another control). An offset that would land on another control is
dropped whole: the element keeps its placed position.

Each geometry token moves its element only in the directions it has room in:

| Element (token) | Moves | Why |
|---|---|---|
| Player details (`--hud-player-details-dx`, `-dy`) | either way | clamped between the HUD band, the field sides and the hand; refused onto another reserved panel, control or target footprint |
| Selected enemy nameplate (`--hud-enemy-nameplate-dy`) | up or down | the visible name/HP footer and its tap target move together; clamped to the field; refused onto the HUD, ribbon, tools, hand, the player's panel, another fighter's controls or another packed target |
| Turn ribbon (`--hud-turn-ribbon-dy`) | down only | it hangs from the HUD band's bottom edge, so a negative value is ignored (it would go under the band); clamped to the field floor |
| Combat log / Reaction row (`--hud-tools-dy`) | up only | it docks on the hand's top edge, so a positive value is ignored (it would cover the cards); clamped to the combat screen top; refused onto the header, ribbon, intents, HP plates, Inspect buttons or fighter targets |

## Studio mapping

`tools/hud-component-studio/css-bindings.json` maps scene nodes to tokens.
Geometry tokens are the node's offset from its seed position in design space
(512-wide canvas), multiplied by `390 / 512` and rounded to whole px. Style
tokens are read from the node's shadow, backing, fill, stroke and font
properties. The studio's form-factor toggle (Mobile / Tablet / Desktop /
Widescreen) keeps a separate set of overrides per form factor; **Export CSS
JSON** writes the current form factor's file, or all four as separate files.

An export carries only the tokens whose value differs from the studio's seed
(the layout as shipped in `tools/hud-component-studio/scene.json`). An untouched
studio exports `"tokens": {}` for every form factor, so exporting without edits
changes nothing in the game. Export-settings values (`minWidth`, `maxWidth`,
`span`) count as set once the designer sets them in the Inspector.

Each binding names the view (`state`) where its component is shown, and the
export reads the node in that view: the enemy nameplate and enemy panel border
in *Enemy selected*, the idle HP plates (`--hud-text-plate-*`) in *Idle*,
everything else in *Player selected*. On Mobile with **Edit all views** off, an
edit to a token-bound component made in another view is not exported; the
Inspector says so ("Exports from <view>").

**Import CSS JSON** accepts every committed `content/hud-layout/*.json`.
A shadow the canvas cannot draw as one design-px layer (several layers,
`inset`, `rem`/`em`) keeps its CSS text and exports verbatim until its first
layer is edited; then the edit replaces that layer and the others are kept.
A unitless `0` is a length; `--hud-header-hp-max-width` may be a `%`, `rem` or
`em` length, kept as text. Re-exporting an untouched import yields the same
tokens, except one whose value equals the studio seed (not exported; `--merge`
keeps it). The imported tokens become that form factor's baseline: a baseline
token whose value is later reset to the seed exports as `null`, so `--merge`
removes the committed override. Without an import, an export never holds `null`.

Workflow:

1. **Export CSS JSON** in the studio (this form factor, or all four) downloads the files.
2. `node tools/hud-layout-css.mjs --merge ~/Downloads/<ff>.json …` validates each
   file and merges it into `content/hud-layout/<ff>.json`: an exported value
   wins, and tokens the export does not carry keep their tuned value. Any refused
   file writes nothing and exits 1. An exported `null` deletes that token's
   override. The stylesheet is regenerated in the same run.
3. Rebuild.
