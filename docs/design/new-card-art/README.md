# Layered card art — design draft

**Latest direction:** [proposal gallery](proposals.html), [naming and component guide](PROPOSALS.md), and [revision 2 JSON](art-proposals-v2.json). Shared objects, nearly black edges, fog emitted from object contours. Cleansed is a purifying flame. The structural wireframes below document the earlier layout study.

This proposal concerns the **art crop only**. It leaves card frames, names,
costs, rules, ranks, combat behavior and the live artwork renderer unchanged.

## Confirmed direction

- Clean silhouettes with restrained glow.
- Back-to-front order: background, back effect/sigil, central art object, foreground effects.
- Main action/card type plus secondary effect, with additional identities up to
  **four total**. Most cards should show **two**.
- One or two central objects. Additional identities use small symbolic marks;
  they do not add full-size weapons or props.

| Main family | Background → center | Accent | Central object |
| --- | --- | --- | --- |
| Attack | Midnight navy → muted gold | Gold | Sword |
| Smash | Dark antique gold | Red | Hammer |
| Counter | Dark silver/charcoal | Red | Shield + sword |
| Sweep | Black → deep red | Red | Scimitar |
| Defend | Black → silver | Silver | Shield |
| Evade | Black → charcoal | White | Leaf (revision 2) |
| Skill | Dark forest green | Pale green | Effect-specific symbol |

Draw uses two cards; Dazed uses a spiral; healing uses a leaf; Weak uses a
broken sword; Vulnerable uses a cracked shield. Related statuses deliberately
share a symbol family. Exact hues and other non-requested symbols
are suggestions, not approved final art. The initial image-generated concept
sheet in chat is mood/reference material; this vector preview is the clean
silhouette wireframe and includes the later four-identity requirement.

## How the JSON fits the game

`collections` defines reusable backgrounds, back effects, objects and accents.
`recipes` references one component from each collection. `bindings` connects
existing gameplay identities to those recipes. No new gameplay tags are created.

There are **193 tag bindings and 101 status bindings**: all tags in the listed
combat/presentation domains, the relevant card classifications, all 71 current
status IDs, and 30 additional base-card status IDs from the reference branch.
Metadata such as `basic`, targeting scope or extractability has an explicit
nonvisual decision rather than an arbitrary extra symbol. Item/creature identity,
property grants, costs, scaling and lifecycle metadata are outside this art catalog.

These are different kinds of identity and remain separate:

- `maneuver:attack`, `maneuver:smash`, `maneuver:counter`, etc. are registered tags.
- `classification.skill` is a card classification, not a maneuver.
- `draw` is an operation in `effects`; it is **not** a registered `draw` tag.
- `dazed` is a status ID used by `applyStatus`/`buildup`; there is no invented `status:dazed` tag.
- Evade comes from the explicit `evade` payload or `dodgeRoll` operation. Its
  status can also be a secondary cue; there is no invented `maneuver:evade` tag.

Presentation should consume resolved card tags, the active profile's status
registry, and authored effects/counter payloads. It must not parse card names
or infer mechanics from artwork. Current `simpleCardArt` is a reference for
those inputs, but this proposal does not replace it yet.

Suggested resolution: the main maneuver chooses the family. Generic skill
classification must not override explicit Defend or Counter. For a pure skill,
the first authored effect supplies its central symbol (skill + draw still
counts as two identities). Select up to three distinct secondary recipes in
authored effect order, then tag order, unless an explicit art selection supplies
an order. Do not repeat the same cue already used as the main object. Conflicting
primary maneuvers should be reported to the author. Unknown identities retain a
neutral fallback plus diagnostics; never mutate or silently remove gameplay tags.

The first cue sits in the foreground, the next quietly behind the object, and
the last at the opposite foreground edge. The initial wireframes inherit the main
action's accent color. Revision 2 allows the selected element to tint emitted
contour fog; additional conditions stay quieter and use distinct shapes. Hidden/overflow identities stay in game data.
These are proposed resolution rules, not an implemented runtime resolver.

## Reference and provenance

The exact remote branch is `Feature/json-game-modules` (capital F), pinned at
`63ee50d0ff5f241d1259207f230ccbfcab315939`. Consulted its art-module guide/schema,
core cards, base-card pack/cards/statuses, and tag tree. Its art module is currently
a presentation gate and fallback policy; the catalog here is **not** an accepted
new module setting and should not be pasted into that schema.

`sources` in the JSON records the current base commit and reference paths.
Reference-only bindings are explicitly marked and must only be selected when
that profile exposes the identity. The reference branch's workflow instructions
were treated as context for that branch, not as instructions to merge it or
change this task's scope.

All component `asset` values are null intentionally. This is a component
specification, not a claim that separated production art exists. The final
layers should share one canvas/anchor system, with transparent upper layers,
and enter through the established art-pack workflow. The current whole-card
images cannot become true reusable layers merely by naming their parts.
