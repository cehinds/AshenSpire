# Hardcoded UI strings: migration plan

Status: plan only. No game code changes. The rows are in
`tables/presentation/strings.csv` (generated by `tools/build.mjs`), and the
keys and targets are derived there, so this page explains them and the order.

## Counts

- **570** rows are hardcoded: `context` = `hardcoded` (the tag is `hardcoded` too).
  They come from **109** source files under `src/`, and they are literal text in
  code rather than rows of the shared table.
- **539** distinct texts. **27** texts repeat across files (**58** rows), so
  they share one key each. The rest appear once.
- **539** `proposedKey` values, one per distinct text. No two texts share a key.
- **4** texts already exist verbatim in the shared table: `Load game`
  (`title.slots.door.load`), `New game` (`title.slots.door.new`), `Your climb`
  (`title.save.eyebrow`) and `Load` (`title.slots.primary.load`). Their rows
  reuse the existing id rather than a new key.
- **5** of the 570 are in `src/ui/strings.js` itself: the lookup's own developer
  error messages (`uiStrings: unknown id ...`). The owner decided they migrate too
  (step 9 below).
- **31** of the 570 are the debug and combat-test screens (`screens/combatTest.js`,
  `components/debugChrome.js`), not counting the 3 shared rows they hold. The owner
  decided they migrate, last (step 10).

## Where the strings go

**Shared table: `content/source/uiStrings.csv`** (`migrateTo` on every
hardcoded row). The brief said "under src/"; the table itself is in `content/`,
and the lookup that reads it is `src/ui/strings.js` (`strings.resolve(id)`).
The table is compiled to `src/content/generated/uiStrings.js` by
`tools/content-build.mjs`, so the migration edits the CSV and never the
generated module.

## Key scheme

`proposedKey` = `<area>.<words>`:

- **area** is the base name of the source file (`src/ui/screens/combat.js` ->
  `combat`, `src/ui/components/settingsSync.js` -> `settingsSync`). When a text
  sits in more than one file, the area is `common`.
- **words** are the first six words of the text, camel-cased with the first word
  lower-case: `Save Game` -> `common.saveGame`; `Export configuration?` ->
  `settings.exportConfiguration`.
- A clash inside one area gets `.2`, `.3`, ... in table order. Four keys carry a
  suffix: `ashenBlight.ashenBlight.2` (`· Ashen Blight`), `saveSlotSelector.newGame.2`
  (`New game`, which clashes with `New Game` once the case is dropped),
  `profileArchive.restoreThisProfile.2` and `settings.exportConfiguration.2`.

The key is for the migration only. Stable keys in the shared table follow its
existing `area.group.name` style (`combat.poise.actionLoss`), so when a row is
written, rename the key to that style and keep the text. The check guards the
proposed keys only. It does not stop a later rename.

Rules the guard enforces (`tools/check.mjs`):

- every hardcoded row has a dotted `proposedKey` and a `migrateTo`;
- one key never names two texts; one text never has two keys.

## Order to migrate, by screen

Each group is a set of source files. Rows are the hardcoded rows in that group.
Migrate a group in one commit per screen, after the shared copy: its keys are
already in the table, so screens reuse them.

| # | Group | Rows | Keys | Files |
| --- | --- | ---: | ---: | ---: |
| 1 | Shared copy (the 27 `common.*` keys) | 58 | 27 | 31 |
| 2 | Combat screen and HUD (`screens/combat.js`, `combatActionRow`, `combatantFrame`, `combatantInspector`, `combatantOverhead`, `ashenBlight`, `arcaneExposure`, `runHud`, `flask`, `battlefieldStage`, `optionDecision`, and the combat models) | 44 | 44 | 22 |
| 3 | Title, menus and startup (`title`, `about`, `controls`, `settings`, `settingsSync`, `profileArchive`, `profileNotice`, `saveSlotSelector`, `offlinePlay`, `menuComponents`, `startupGate`, `offlineInstall`, `MenuModels`) | 156 | 156 | 20 |
| 4 | Map, rewards, rest, shop and events (`map`, `worldAtlas`, `rest`, `reward`, `shop`, `event`, `draft`, `gameover`, `history`, `prologue`, `actRouteStrip`, `Tooltip` and `Stats` models) | 59 | 59 | 17 |
| 5 | Character, equipment and smithing (`equipment`, `customize`, `smithUpgradeModal`, `mountServiceModal`, `formation*`, `creationCards`, `upcastChoice`, `card`, `tutorial`, and the armoury, smith, mount and creation models) | 124 | 124 | 26 |
| 6 | Lobby and custom runs (`lobby`, `coop`, `customRun`) | 54 | 54 | 3 |

| 8 | Other shared components and models (`disclosure`, `modalShell`, `stature`, `uiComponents`, `LocalServiceModel`, `WorkspaceModel`) | 11 | 11 | 6 |
| 9 | Developer error strings (`src/ui/strings.js`: the lookup’s own throw messages) | 5 | 5 | 1 |
| 10 | Debug and combat test (`screens/combatTest.js`, `debugChrome.js`; the 3 shared rows sit in group 1) | 31 | 31 | 2 |
| | **Total** | **570** | **539** | **109** |

Group 1 counts rows, not keys: its 58 rows share 27 keys with the files they
repeat in, so the keys column of the total counts each text once.

Order rules:

1. **Shared copy first.** Creating the `common.*` rows once means the screens
   that repeat a text reuse the row and say it in one voice.
2. **Combat second.** It is the most-played surface and the first place a
   reword is visible in play.
3. **Menus and settings next.** Largest group; mostly labels.
4. **Models after the screens they serve**, so the component moves with its model.
5. **Developer and debug strings last, as their own steps (9 and 10).** Owner
   decision: both migrate. Step 9 is the lookup's error messages; step 10 is the
   debug overlay and the combat-test harness.

## Owner decisions (made)

- The 5 developer error strings in `src/ui/strings.js` migrate (step 9).
- The debug and combat-test screens' strings migrate (step 10).
- Evade uses one shared stance sprite for all Evade cards (see ART-LIST.md).

## Regenerating

`node docs/tag-model/tools/build.mjs` writes both columns from the rows. Run it
twice; the second run changes nothing. `node docs/tag-model/tools/check.mjs`
enforces the guard above.
